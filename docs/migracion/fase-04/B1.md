# B.1 — Corrección acotada de contratos y auditoría del bloque B

## Alcance y aceptación congelados antes de validar

Baseline explícito: `2f95273` (bloque B registrado). No se adelantan routers/S-03/S-08 del bloque C ni concurrencia del D. No cambiar esquema, modelo, CSV, permisos, consentimiento ni diferencias POST/PATCH.

1. Recuperar los payloads/eventos de liberación del bloque A: PATCH con cupo nuevo o existente, liberación explícita y cancelación con liberación. Comprobar ID generado, before/after, unicidad y orden histórico de eventos de cancelación.
2. Rechazar `REPROGRAMADA` en la operación componible pública sin mutar fecha/estado ni añadir historial/auditoría. La reprogramación completa conserva su endpoint existente.
3. Operaciones públicas por IDs y snapshots inmutables; no devolver filas ORM. Citas conserva validaciones/transiciones, Lista de Espera construye sus cupos. Eliminar fábrica ORM inyectable y autoimportación. Mantener el contrato ORM histórico dentro de Citas, no como API pública ajena.
4. Mantener los locks existentes y un solo commit coordinador. La coordinación sigue en los servicios existentes; no se declara una nueva capa de workflows ni se certifica concurrencia todavía.
5. Pruebas focalizadas, regresión completa caracterizada, paridad OpenAPI/DDL/predicciones y cobertura ≥75 %. S-02/S-03 siguen históricos; nunca convertirlos en suite verde.
6. PostgreSQL nuevo y aislado: fallo inducido después del flush del cupo y rollback de cita, respuesta, historial y auditoría comprobado desde una conexión independiente.
7. Evidencia exclusiva por run-id, fuentes por hash, commit de implementación identificado y JUnit sanitizados. El commit de resultados no modifica código.

Los JOIN de lectura en repositorios y el acceso relacional de enriquecimiento quedan explícitamente pendientes de los adaptadores de lectura de fase 4. Esta corrección prohíbe imports de ORM/reglas privados ajenos en los tres servicios, pero no afirma que toda composición de lectura de la aplicación ya esté desacoplada.

## Procedimiento

Primero registrar implementación y pruebas con Git limpio. El harness usa la imagen de dependencias de fase 3 **por ID**, montando fuentes RO: no es un nuevo build empaquetado de fase 4 (pendiente del D).

```powershell
python -B docs/migracion/fase-04/validar.py preparar --scope B1 --baseline-ref 2f95273 --run-id bloque-b1-20261105-02
python -B docs/migracion/fase-04/validar.py baseline --run-id bloque-b1-20261105-02
python -B docs/migracion/fase-04/validar.py actual --run-id bloque-b1-20261105-02
python -B docs/migracion/fase-04/validar.py detener --run-id bloque-b1-20261105-02
python -B docs/migracion/fase-04/validar.py resumen --run-id bloque-b1-20261105-02
python -B docs/migracion/fase-04/publicar.py --run-id bloque-b1-20261105-02
```

Usar un ID nuevo para cada intento. No sobrescribir, borrar ni reutilizar laboratorios anteriores. Ante error, detener solo el laboratorio de la ejecución conservando contenedor/red/volumen. El escenario de rollback independiente y el de identidad conservan datos QA sintéticos únicamente en el volumen nuevo de pruebas; no se ejecuta seed ni se copian datos del principal.

Verificación de paquete (no reejecuta pruebas ni certifica fuentes posteriores):

```powershell
python -B docs/migracion/fase-04/publicar.py --run-id bloque-b1-20261105-02 --verify-only
```

Frontend no reejecutado. No se modifican sus fuentes ni configuración.
